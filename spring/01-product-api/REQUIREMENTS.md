# 상품 API 요구사항

## 먼저 할 일과 완료 기준

서버를 시작하고 `products.http`의 등록 → 단건 조회부터 직접 구현한다. **등록 201, 조회 200, 잘못된 입력 400, 없는 ID 404, 중복 ID 409**를 구분하고 실패한 요청이 기존 상품을 바꾸지 않으면 필수 기능의 기준을 충족한다. 아래의 기능 테스트까지 작성해 확인한다.

현재 골격에는 엔드포인트가 없어 요청의 입력값과 관계없이 `/products` 경로에서 404가 예상된다. 아래 표와 예제는 **구현 후 지켜야 할 계약**이다.

## 공통 필드와 저장 규칙

| 필드 | API에서 사용하는 값 | 필수 규칙 |
| --- | --- | --- |
| `id` | 클라이언트가 지정하는 JSON 정수, Java `Long` 범위 | 누락·null·숫자로 해석할 수 없는 값·범위 초과는 400. 자동 생성하지 않는다. 기존 실습과 같이 ID의 양수 제한은 두지 않는다. |
| `name` | JSON 문자열 | 누락·null·빈 문자열·공백만 있는 문자열은 400. |
| `price` | 정수 원, Java `int` 범위 | 누락·null·음수·범위 초과는 400. 0은 허용한다. |
| `stock` | 정수 수량, Java `int` 범위 | 누락·null·음수·범위 초과는 400. 0은 허용한다. |

- 요청은 `Content-Type: application/json`으로 보내고 성공 응답은 JSON이다.
- ID는 `-9223372036854775808`부터 `9223372036854775807`까지, 가격·재고의 유효 범위는 `0`부터 `2147483647`까지다.
- 예제에서 ID·가격·재고는 따옴표 없는 정수로 보낸다. JSON 소수나 숫자 문자열의 자동 형변환을 엄격하게 차단하는 설정은 선택 심화이며 오늘 필수 검증 범위에 포함하지 않는다.
- 서버 프로세스 안에서 같은 Inventory 인스턴스의 메모리를 사용한다. 처음에는 비어 있고 재시작하면 초기화된다.
- 상품의 네 필드를 저장한 뒤 단건 조회에서 같은 값을 돌려준다. 가격·재고를 임의로 보정하거나 누락 값을 0으로 취급하지 않는다.
- 요청 형식과 필드가 유효한지 먼저 확인하고 중복 여부를 판단한다. 유효한 필드의 중복 ID 요청은 409다.

## 1. 상품 등록 — POST /products

요청:

```http
POST /products
Content-Type: application/json

{"id":101,"name":"노트","price":1000,"stock":10}
```

성공 응답 예시:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /products/101

{"id":101,"name":"노트","price":1000,"stock":10}
```

`Location`은 생성한 상품의 단건 조회 주소다. `/products/101` 형태의 상대 경로 또는 그 경로로 끝나는 유효한 절대 URL을 허용한다. JSON 속성의 순서와 공백은 비교하지 않는다.

| 상황 | 상태 | 데이터에 미치는 영향 |
| --- | ---: | --- |
| 유효한 새 ID 등록 | 201 | 상품 한 개가 추가된다. |
| JSON 문법 오류, 본문 누락, 필드 누락/null/유효성 위반 | 400 | 아무 상품도 추가하지 않는다. |
| 이미 등록된 ID를 유효한 값으로 다시 등록 | 409 | 원래 상품의 이름·가격·재고를 덮어쓰지 않는다. |

## 2. 상품 단건 조회 — GET /products/{id}

`GET /products/101`의 성공 응답 예시:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":101,"name":"노트","price":1000,"stock":10}
```

| 상황 | 상태 | 기준 |
| --- | ---: | --- |
| 등록된 ID | 200 | 등록한 네 필드를 반환한다. 조회로 상태가 바뀌지 않는다. |
| 올바른 Long 형식이지만 등록되지 않은 ID | 404 | 예: 초기 상태의 `/products/999` |
| Long으로 변환할 수 없는 경로 값 또는 범위 초과 | 400 | 예: `/products/abc`, `/products/9223372036854775808` |

오늘은 목록 조회, 수정, 삭제 경로를 만들지 않는다. 필수 두 경로를 먼저 완성한다.

## 오류 처리의 크기

필수 계약은 위 상태 코드와 데이터 보존이다. 오류 본문의 통일된 JSON 형식이나 문구는 오늘 고정하지 않으므로 Spring의 기본 오류 응답을 사용해도 된다. Controller의 분기나 작은 예외 변환으로 시작할 수 있다. 도메인의 모든 예외를 무조건 400으로 바꾸면 중복 등록의 409를 놓칠 수 있으므로 구분한다. 예외 메시지 문자열을 파싱해 상태를 고르는 방식은 피한다.

## 직접 확인할 순서

1. 새 서버에서 ID 101을 등록해 201·Location·응답의 네 필드를 확인한다.
2. 다음 요청에서 ID 101을 조회해 200과 등록한 값을 비교한다.
3. 같은 ID로 다른 값을 등록해 409를 확인한 뒤 다시 조회해 원래 값이 남아 있는지 확인한다.
4. ID 102는 가격·재고 0으로 등록하고 조회한다. 둘 다 0인지 확인한다.
5. 가격만 음수인 요청과 재고만 음수인 요청을 각각 보내 400을 확인한다. 해당 ID를 조회하면 404여야 한다.
6. 필드 누락/null·빈 이름·공백 이름을 확인한다. 특히 재고 누락이 0으로 등록되지 않아야 한다.
7. 없는 ID는 404, 숫자가 아닌 ID와 Long 범위 초과는 400인지 확인한다.
8. JSON 문법이 깨진 요청과 빈 본문은 400이어야 한다.
9. 서버를 종료하고 재시작한 뒤 기존 ID 101 조회가 404인지 확인한다.

1–7의 핵심 결과를 자동 테스트로 옮긴다. 각 테스트는 새로운 Inventory 또는 독립적인 ID와 준비 데이터를 사용해 앞 테스트에 기대지 않게 한다. 재시작 확인은 오늘 수동 확인으로 충분하다. 기본 `contextLoads()` 통과와 API 기능 테스트 통과를 구분해 기록한다.

## 오늘의 한계

메모리 저장과 순차 요청이 실습 범위다. 동시 중복 등록의 원자성, 영속성, 운영 배포, 공통 예외 프레임워크는 완료 조건이 아니다. 이전 Product/Inventory의 규칙을 확인하면서 HTTP 입출력에 필요한 연결을 직접 작성한다.
